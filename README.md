# Saee Life Herbal

A responsive core-PHP/MySQL agricultural product website, CMS and member portal. The public website and admin have separate installable PWA manifests. The basket creates order requests; the system does **not** automatically collect payments, issue refunds or send bank transfers.

## Installation and upgrades

1. Use PHP 8.1+ with PDO MySQL, DOM, fileinfo, OpenSSL and sessions, plus MySQL 5.7/8 or compatible MariaDB. Create an empty UTF-8 database and import `schema.sql`, `migration-002.sql`, `migration-003.sql`, `migration-004.sql`, `migration-005.sql` and `migration-006.sql`, **in that order**. An existing 005 installation should import only 006; an existing 004 installation should import 005 then 006, an existing 003 installation should import 004 through 006, and an existing 002 installation should import 003 through 006 in order. Migrations are not idempotent. Take a tested backup, take the site offline and stop workers before upgrading.
2. Copy `api/config.example.php` to `api/config.php` and configure the database, business timezone, HTTPS `public_url`, verified `mail_from`, and a unique encryption key. Generate a key with `php -r 'echo base64_encode(random_bytes(32)), PHP_EOL;'`. Keep the key secret, restrict access to config, and back up the key **separately** from the database. If it is lost or changed without a successful rotation, encrypted records cannot be read. See the key-rotation procedure below. The application refuses to run without a valid key. Configure the server's PHP `mail()` transport and verify delivery before enabling password recovery or email verification.
3. With the site still offline, run `php api/encrypt-existing.php`. This converts legacy member KYC/bank fields and payout bank snapshots to authenticated AES-256-GCM ciphertext in a transaction and clears the old plaintext columns. It is safe to run again after a completed migration; it stops if encrypted and plaintext values conflict. Keep historical backups protected: this script does not alter previous backups. Restore and verify backups and the key before allowing real use.
4. Create the first administrator once: `php api/create-admin.php 'Admin Name' admin@example.com 'a-strong-password'`. The administrator is also the default company sponsor, `COMPANY`. Use a unique strong password, and avoid leaving the command in shared shell history.
5. Make `uploads/` writable by PHP. Set `upload_max_filesize` to at least `30M` and `post_max_size` above that for video uploads. On Apache, the included `uploads/.htaccess` blocks script execution. On Nginx or another server, explicitly disable script execution in `/uploads/` and deny public access to `.git`, SQL files, test files, backups and configuration. Serve over HTTPS and configure the server to process `.php` files. For local development use `php -S 0.0.0.0:8000` from the project root.
6. Open `/admin/index.php` to sign in and `/website/index.php` for the public website. Add real products, slides, pages, social links and business details before launch. Seeded products and product imagery are illustrative; seeded products are marked as samples and cannot be ordered until edited. The company sponsor ID must belong to an existing member.

If PHP or the database is unavailable, the root public shell can show sample content for a visual preview; login, checkout and admin **cannot save anything** in that mode. The named PHP pages require a PHP web server, not a static preview or a `file://` URL. PWA installability requires HTTPS or localhost. Offline caching is limited to the shell, not live account or API data.

## Project structure and page URLs

- `admin/` contains named admin entry pages such as `products.php`, `pages.php` and `settings.php`, plus the admin panel UI in `panel.js`.
- `website/` contains named public/member entry pages such as `about.php`, `products.php`, `login.php` and `register.php`, plus public/member presentation code in `pages.js`.
- `includes/site-shell.php`, `index.html` and `assets/` provide the shared layout, navigation and styling; `api/` provides authenticated PHP endpoints backed by MySQL. Existing `/#admin` and other hash bookmarks remain supported.
- Pages created in the CMS are stored in the MySQL `pages` table under their unique slug and served at `website/page.php?slug=your-page-name`. They do not create executable PHP files on the server. Products, settings, slides and other admin records are stored in their respective MySQL tables; uploaded media files are in `uploads/`, with their references stored in MySQL.

### If admin changes are not saved

1. Make sure the site is served by PHP and that `api/config.php` points to the intended, persistent MySQL database. Import the schema and all required migrations in order, and create the administrator as described above. A static preview is not connected to a database.
2. Open `api/index.php?action=bootstrap` on the same site: it should return JSON, not a PHP source file, missing-configuration message or database error. Check PHP/server logs and the configured DB user’s permissions if it does not. Do not share database credentials.
3. Sign in at `/admin/index.php`, save a small change, and reload that page to confirm it. If a save reports a follow-up or connection error, reload and check before retrying; an earlier step may already have been saved. File uploads additionally require a writable `uploads/` directory.
4. Back up the database and configuration key. Do not use an ephemeral test database for real content; replacing or resetting a database will remove its saved records.

## Workflows

- **CMS:** Manage pages, homepage copy, contact/brand settings, logo and favicon, social icons and carousel slides. Product descriptions and pages use sanitized rich text; products support multiple image and MP4/WebM uploads (30 MB each, MIME checked). Navigation labels, homepage calls to action and the homepage feature image are also configurable. Some interface labels and decorative template copy remain fixed.
- **Orders and refunds:** Members submit an order request; no payment is collected online. After external payment, an admin confirms the pending order with a unique receipt. Alternatively, an admin can record a separately confirmed purchase. Each line credits the buyer's direct sponsor and that sponsor's sponsor at the configured fixed per-unit amounts. Receipt references are unique across both paths. After an external customer refund, an admin can record a partial quantity return on a purchase line or return all remaining items on an order. The entered customer refund amount cannot exceed the recorded product value of the returned units; shipping is not included. Sponsor commissions are reversed proportionally to returned quantities in integer paise, with cumulative rounding so full returns reverse the original credits exactly. Unique refund references and quantity limits prevent duplicate reversals. Returns spanning multiple partial lines must be recorded as separate refunds with separate references. A reversal is blocked if a sponsor has insufficient available wallet balance; reconcile the wallet before recording it. Customer transfers, milestone/royalty clawbacks and negative-balance debt handling are not automated.
- **Members and account recovery:** An optional sponsor ID defaults to the company ID. Members see wallet activity and direct referrals and can submit optional KYC/bank information; changes revoke verification. Admins review details manually, not through an identity provider. Password reset uses a 30-minute single-use email link, revokes existing sessions, and requires a configured HTTPS public URL and working mail transport. Responses do not disclose whether an account exists. Members can also request a 24-hour, single-use email verification link from their account. Existing emails start unverified after migration; email verification is informational and does not replace manual KYC or block purchases or payouts.
- **Rewards:** Milestone rules pay once when the direct-referral threshold is reached during registration. Monthly royalties use the **current** direct-referral count and can run manually from admin or with `php api/run-royalties.php`. Runs are idempotent per member/rule/month. A cron job can run this regularly, e.g. with a business-timezone scheduler: `55 23 * * * cd /path/to/site && /usr/bin/php api/run-royalties.php`. Each eligible member is credited on the first successful run after meeting the threshold in that month. Only the current month can be run; this is not a historical eligibility snapshot. Awarded rules cannot be edited or deleted.
- **Payouts:** Verified, complete KYC/bank information and sufficient wallet balance are required. A request reserves funds; admins approve, reject (refunds the reservation), or mark an approved payout paid after an external transfer. Bank details must still match the original request. CSV exports contain sensitive data and must be protected. Member KYC/bank fields and payout bank snapshots are encrypted at rest, but names, emails, phone numbers, order addresses, reports, application memory and logs are not encrypted by that mechanism.
- **Staff access:** Owners can create, disable and change the roles of non-owner staff. Content staff can manage pages, products, carousel, marketing copy and social media, but cannot change commission amounts or financial settings. Operations staff can view orders and review member KYC; finance staff can confirm purchases, administer rewards and payouts, and record full or partial refunds. Operations and finance staff can view sensitive member details. Role or activation changes revoke existing staff sessions. Owner accounts cannot be changed from the staff screen. Distribute temporary passwords securely and ask staff to reset them.
- **Admin two-step verification:** Every administrator can opt in from the Security tab using an authenticator app (TOTP) and must save the one-time recovery codes shown during setup. Correct server time is essential. Enabling or disabling verification revokes the account’s other sessions. Password reset does not disable two-step verification. If every recovery code is lost, a trusted server operator can run `php api/reset-admin-mfa.php admin@example.com`; this disables it, revokes sessions and records an audit event. Restrict shell and database access and re-enroll immediately after recovery. Two-step verification is not enforced until each administrator enables it.
- **Activity:** The admin panel displays recent administrative actions, including payout CSV exports and refund records. Most entries are best effort and are not tamper-proof; refund events are recorded in the same transaction as the reversal. Forward logs to an independent protected system for compliance-grade auditing.

## Rotating the encryption key

Take the website, background workers and royalty cron offline. Make and verify backups of the database **and the old configuration/key**, stored separately and securely. Create a protected new configuration file outside the web root with the same database DSN and user but a newly generated 32-byte base64 key. Run `php api/rotate-key.php /secure/path/new-config.php` using the old `api/config.php`. The script rejects unmigrated plaintext, decrypts and re-encrypts member, payout and administrator authenticator secrets in one database transaction, and records a rotation event. Only after it reports success, atomically update `api/config.php` to the new configuration, restart PHP workers to clear cached configuration, verify access to existing member and payout records and administrator authenticator sign-in, and restore service. Keep both keys securely until the backup-retention period ends. If interrupted or uncertain whether the database committed, keep the site offline: determine the active key from the rotation event or restore the matching tested database backup and configuration; do not discard either key. The script does not rotate old backups.

## Verification

`tests/integration.py` is a destructive smoke test for a **fresh disposable database** and running PHP server. Import all six SQL files, configure a test encryption key, create the test admin as above, then run `BASE_URL=http://127.0.0.1:8000 ADMIN_EMAIL=admin@example.com ADMIN_PASSWORD='...' python3 tests/integration.py`. Set `BUSINESS_TIMEZONE` if different from Asia/Kolkata. Tests cover persistence across sessions, invalid record IDs, authenticator verification and one-time recovery codes, role authorization, uploads, content sanitization, sponsor credits, duplicate receipts, order confirmation, refunds, royalties, KYC, CSV and payouts. To test email verification with a local test mail sink, configure PHP `sendmail_path` to write mail to a disposable file and set `TEST_MAIL_CAPTURE` to that file. Never use a test sink for real mail. Run `php tests/crypto.php` for encryption tamper checks, `php tests/mfa.php` for TOTP vectors, `php tests/refund-math.php` for partial-refund rounding checks and `node --test tests/admin-route.cjs tests/navigation.cjs` for route checks. Do not run it against real customer data.

## Before production

This is not a certified payment, banking or MLM platform. There is no payment gateway, automated bank payout or external identity verification integration, multi-line partial-refund batching or a tamper-proof audit trail. Admin two-step verification is optional and requires each administrator to enroll. Payments, payouts and KYC review remain manual by choice. Login throttling is basic and not a substitute for edge protection. Before handling real customer data or money, arrange independent security and privacy testing, key management, backups and retention policies, monitoring, reconciliation, fraud controls and an audited payment/payout integration. Obtain professional legal advice on Indian direct-selling/MLM, agricultural-product, privacy and consumer requirements, and disclose actual plan terms to members.
