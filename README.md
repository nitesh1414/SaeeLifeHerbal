# Saee Life Herbal

A responsive core-PHP/MySQL agricultural product website, CMS and member portal. The public website and admin have separate installable PWA manifests. The basket creates order requests; the system does **not** automatically collect payments, issue refunds or send bank transfers.

## Installation and upgrades

1. Use PHP 8.1+ with PDO MySQL, DOM, fileinfo, OpenSSL and sessions, plus MySQL 5.7/8 or compatible MariaDB. Create an empty UTF-8 database and import `schema.sql`, `migration-002.sql` and `migration-003.sql`, **in that order**. An existing 002 installation should import only `migration-003.sql` once. Migrations are not idempotent. Take a tested backup, take the site offline and stop workers before upgrading.
2. Copy `api/config.example.php` to `api/config.php` and configure the database, business timezone, HTTPS `public_url`, verified `mail_from`, and a unique encryption key. Generate a key with `php -r 'echo base64_encode(random_bytes(32)), PHP_EOL;'`. Keep the key secret, restrict access to config, and back up the key **separately** from the database. If it is lost or changed, encrypted records cannot be read; key rotation is not automated. The application refuses to run without a valid key. Configure the server's PHP `mail()` transport and verify delivery before enabling password recovery.
3. With the site still offline, run `php api/encrypt-existing.php`. This converts legacy member KYC/bank fields and payout bank snapshots to authenticated AES-256-GCM ciphertext in a transaction and clears the old plaintext columns. It is safe to run again after a completed migration; it stops if encrypted and plaintext values conflict. Keep historical backups protected: this script does not alter previous backups. Restore and verify backups and the key before allowing real use.
4. Create the first administrator once: `php api/create-admin.php 'Admin Name' admin@example.com 'a-strong-password'`. The administrator is also the default company sponsor, `COMPANY`. Use a unique strong password, and avoid leaving the command in shared shell history.
5. Make `uploads/` writable by PHP. Set `upload_max_filesize` to at least `30M` and `post_max_size` above that for video uploads. On Apache, the included `uploads/.htaccess` blocks script execution. On Nginx or another server, explicitly disable script execution in `/uploads/` and deny public access to `.git`, SQL files, test files, backups and configuration. Serve over HTTPS and configure the server to process `.php` files. For local development use `php -S 0.0.0.0:8000` from the project root.
6. Visit `/#admin`, add real products, slides, pages, social links and business details before launch. Seeded products and product imagery are illustrative; seeded products are marked as samples and cannot be ordered until edited. The company sponsor ID must belong to an existing member.

If PHP or the database is unavailable, the public shell falls back to sample content for a visual preview; login, checkout and admin are not operational in that mode. PWA installability requires HTTPS or localhost. Offline caching is limited to the public shell, not live account or API data.

## Workflows

- **CMS:** Manage pages, homepage copy, contact/brand settings, logo and favicon, social icons and carousel slides. Product descriptions and pages use sanitized rich text; products support multiple image and MP4/WebM uploads (30 MB each, MIME checked). Some button labels and decorative template copy remain fixed.
- **Orders and refunds:** Members submit an order request; no payment is collected online. After external payment, an admin confirms the pending order with a unique receipt. Alternatively, an admin can record a separately confirmed purchase. Each line credits the buyer's direct sponsor and that sponsor's sponsor at the configured fixed per-unit amounts. Receipt references are unique across both paths. Full order and standalone purchase refunds can be recorded after the external customer refund; this reverses the associated purchase commissions atomically and cannot be repeated. A reversal is blocked if a sponsor has insufficient available wallet balance; reconcile the wallet before recording it. Partial refunds, automated customer transfers, milestone/royalty clawbacks and negative-balance debt handling are not implemented.
- **Members and account recovery:** An optional sponsor ID defaults to the company ID. Members see wallet activity and direct referrals and can submit optional KYC/bank information; changes revoke verification. Admins review details manually, not through an identity provider. Password reset uses a 30-minute single-use email link, revokes existing sessions, and requires a configured HTTPS public URL and working mail transport. Responses do not disclose whether an account exists. Email ownership is not otherwise verified.
- **Rewards:** Milestone rules pay once when the direct-referral threshold is reached during registration. Monthly royalties use the **current** direct-referral count and can run manually from admin or with `php api/run-royalties.php`. Runs are idempotent per member/rule/month. A cron job can run this regularly, e.g. with a business-timezone scheduler: `55 23 * * * cd /path/to/site && /usr/bin/php api/run-royalties.php`. Each eligible member is credited on the first successful run after meeting the threshold in that month. Only the current month can be run; this is not a historical eligibility snapshot. Awarded rules cannot be edited or deleted.
- **Payouts:** Verified, complete KYC/bank information and sufficient wallet balance are required. A request reserves funds; admins approve, reject (refunds the reservation), or mark an approved payout paid after an external transfer. Bank details must still match the original request. CSV exports contain sensitive data and must be protected. Member KYC/bank fields and payout bank snapshots are encrypted at rest, but names, emails, phone numbers, order addresses, reports, application memory and logs are not encrypted by that mechanism.
- **Activity:** The admin panel displays recent administrative actions, including payout CSV exports and refund records. Most entries are best effort and are not tamper-proof; refund events are recorded in the same transaction as the reversal. Forward logs to an independent protected system for compliance-grade auditing.

## Verification

`tests/integration.py` is a destructive smoke test for a **fresh disposable database** and running PHP server. Import all three SQL files, configure a test encryption key, create the test admin as above, then run `BASE_URL=http://127.0.0.1:8000 ADMIN_EMAIL=admin@example.com ADMIN_PASSWORD='...' python3 tests/integration.py`. Set `BUSINESS_TIMEZONE` if different from Asia/Kolkata. Tests cover authorization, uploads, content sanitization, sponsor credits, duplicate receipts, order confirmation, refunds, royalties, KYC, CSV and payouts. Do not run it against real customer data.

## Before production

This is not a certified payment, banking or MLM platform. There is no payment gateway, automated bank payout or identity verification integration, partial refund workflow, email verification, granular staff permissions, MFA, key rotation, or tamper-proof audit trail. Login throttling is basic and not a substitute for edge protection. Before handling real customer data or money, arrange independent security and privacy testing, key management, backups and retention policies, monitoring, reconciliation, fraud controls and an audited payment/payout integration. Obtain professional legal advice on Indian direct-selling/MLM, agricultural-product, privacy and consumer requirements, and disclose actual plan terms to members.
